## 2. Performance

### NFR-PERF-01 — Время ответа API (чтение)
Для 95% успешных read-запросов (каталог, список своих заявок, очередь задач, карточка заявки) время ответа backend при нагрузке до 20 одновременных пользователей ≤ **500 мс** (исключая холодный старт API-сервиса).  
**Проверка:** нагрузочный/смоук-сценарий с замером latency p95.

### NFR-PERF-02 — Время ответа API (запись)
Для 95% успешных write-операций (создание заявки, submit, approve/reject/return) время ответа ≤ **1000 мс** при той же нагрузке.  
**Проверка:** замеры p95 на критичных сценариях.

### NFR-PERF-03 — Пагинация списков
Списки заявок и задач поддерживают пагинацию (уведомления и реестр admin — [docs/backlog.md](../backlog.md)). Размер страницы по умолчанию **20**, максимум **100**.  
**Проверка:** запрос с `page_size=101` отклоняется валидацией.

### NFR-PERF-04 — Baseline объёма данных для performance testing
Система корректно работает при baseline: **минимум 1000 заявок** и **минимум 5000 записей history** без деградации p95 за пределы NFR-PERF-01/02 в локальном/демо-окружении по NFR-DEP-01 (Python + Neon/local PostgreSQL).  
**Проверка:** seed/генерация данных + замер latency.

## 3. Availability


### NFR-AVL-01 — Режим поставки MVP
Целевой режим — локальный/демо-стенд по NFR-DEP-01 (локально Python + Neon/local PostgreSQL; в облаке Render + Neon). SLA production **не применяется**.  
**Проверка:** documented start без Docker Desktop; смоук сценария на локальном или облачном демо-стенде.

### NFR-AVL-02 — Восстановление после рестарта
После перезапуска API сервис продолжает работать с сохранёнными данными PostgreSQL после восстановления соединения с БД; сервер API остаётся **stateless** (без sticky-state / server-side session store).  
**Проверка:** перезапуск API и восстановление соединения с PostgreSQL → ранее сохранённые данные заявок доступны.

## 4. Security


### NFR-SEC-02 — Авторизация по ролям и владению
Доступ разграничивается по ролям и правилам BR-01, BR-14, BR-15, BR-21 (admin-видимость — [docs/backlog.md](../backlog.md)). Нарушение → HTTP 403.  
**Проверка:** AC-ACC-01, AC-ACC-02 и матрица RBAC.

### NFR-SEC-05 — Скрытие чужих ресурсов
Запрос ресурса, существование которого пользователь не должен видеть (например чужая заявка для employee), возвращает **HTTP 404** и `ERR_NOT_FOUND`.  
**Проверка:** AC-ACC-01.

### NFR-SEC-06 — HTTPS
Для любого **внешнего** (публично доступного) демо-стенда HTTPS **обязателен**. При локальном запуске по NFR-DEP-01 (без внешнего доступа) допустим HTTP.  
**Проверка:** конфигурация внешнего стенда / reverse proxy.

## 5. Reliability


### NFR-REL-01 — Целостность перехода статусов
Переходы статусов заявки и задач выполняются атомарно с записью истории: не допускается «approve без истории» или «смена статуса без закрытия задач этапа» при first-approve.  
**Проверка:** интеграционные тесты BR-03, BR-04, BR-05, BR-20.

### NFR-REL-02 — Идемпотентность повторного действия
Повторный approve/reject/return по уже завершённой задаче не меняет состояние повторно и возвращает ошибку duplicate/invalid state.  
**Проверка:** error-matrix ERR_DUP_ACTION, ERR_TASK_DONE.

### NFR-REL-03 — Сохранность RouteInstance
RouteInstance после первого submit неизменяем прикладными операциями.  
**Проверка:** AC-APP-10.

## 6. Maintainability


### NFR-MNT-01 — OpenAPI как контракт
Публичный REST API описывается OpenAPI 3.x и соответствует реализации (после Baseline / будущий контракт API).  
**Проверка:** сверка спецификации и фактических ответов.

### NFR-MNT-02 — Миграции БД
Схема БД управляется миграциями (Alembic или аналог). Запрещены «ручные» необратимые правки схемы на демо без миграции.  
**Проверка:** чистый подъём БД только миграциями.

### NFR-MNT-03 — Трассируемые ID требований
Код и тесты критичных правил ссылаются на ID FR/BR/AC в комментариях или именах тестов для ключевых сценариев согласования.  
**Проверка:** наличие ссылок в тестах approve/reject/return/snapshot.

## 7. Scalability


### NFR-SCL-02 — Рост числа типов заявок
Система поддерживает ≥ **50** активных типов заявок и ≥ **10** этапов на маршрут без изменения архитектуры.  
**Проверка:** seed/test data или SQL/test script с ≥ 50 активными типами заявок и маршрутом из 10 этапов. После реализации Admin UI тот же объём может дополнительно проверяться через UI ([docs/backlog.md](../backlog.md)).

## 8. Logging / Audit


### NFR-LOG-01 — Технические логи API
API логирует: method, path, status code, latency, request_id, user_id (если аутентифицирован). Пароли и токены в лог не пишутся.  
**Проверка:** sample логов на submit (login — [docs/backlog.md](../backlog.md)).

### NFR-LOG-02 — Прикладной аудит заявок
Значимые бизнес-события пишутся в историю заявки (BR-24) с actor, timestamp, action, from/to, comment.  
**Проверка:** UC-14, FR-AUDIT-01.

### NFR-LOG-03 — Retention
1. **Технические логи API:** retention **14 дней** (или ротация по размеру volume с эквивалентным целевым окном).  
2. **История заявок (прикладной аудит):** retention для MVP — **60 дней**.

**Проверка:** конфигурация ротации логов; политика очистки/архивации history (реализация после Baseline).

## 9. Usability


### NFR-USB-01 — Понятность статусов
В карточке заявки пользователь видит человекочитаемый статус и текущий этап (если `in_approval`).  
**Проверка:** UI/демо UC-06.

### NFR-USB-02 — Сообщения об ошибках
Пользовательские сообщения соответствуют error-matrix (поле User message) и не раскрывают stack trace.  
**Проверка:** негативные сценарии forbidden и invalid state (login — [docs/backlog.md](../backlog.md)).

### NFR-USB-03 — Язык интерфейса MVP
UI и пользовательские сообщения — **русский**.  
**Проверка:** смоук UI.

## 10. Deployment


### NFR-DEP-01 — Локальный запуск и облачный деплой
MVP поднимается без Docker Desktop: локально — Python-окружение + управляемая PostgreSQL (Neon) либо локальный PostgreSQL; в облаке — API на Render, БД на Neon. Секреты и URL БД — только через переменные окружения (см. NFR-DEP-03).  
**Проверка:** documented start на машине без Docker; смоук на Render после деплоя (выбор роли → создание заявки → решение согласующего).

### NFR-DEP-02 — Seed-данные
После первого запуска доступны демо-пользователи всех ролей и ≥ 2 активных типа заявок с валидным маршрутом.  
**Проверка:** seed данных + смоук каталога и очереди согласующего (выбор демо-роли; без login).

### NFR-DEP-03 — Конфигурация через env
Секреты (DB URL и др.) задаются переменными окружения, не хардкодятся в репозитории.  
**Проверка:** review конфигурации.
