## 1. Цель системы

Employee Service — веб-сервис подачи и согласования внутренних заявок сотрудников (отпуск, справки и т.п.).

Сотрудник выбирает тип заявки из каталога, заполняет форму, отправляет её на согласование и видит статус. Заявка проходит последовательные этапы согласования, на каждом согласующий принимает решение: согласовать, отклонить или вернуть на доработку.

---

## 2. Цель проекта

Показать на сквозном примере путь системного аналитика: от описания проблемы и требований через процессы, модель данных и архитектуру к API-контракту и работающему MVP.

Главный результат — аналитическая документация. Реализация (FastAPI + PostgreSQL, лёгкий веб-клиент из статических HTML-страниц с JavaScript) нужна, чтобы подтвердить, что спецификации реализуемы.

---

## 3. Проблема

Кадровые и административные вопросы решаются устно или перепиской по почте. Единого места, где видны заявка и её статус, нет. Из-за этого:

- руководитель может забыть о вопросе или затянуть решение;
- у решения нет письменного следа, а кадровая служба требует подтверждение;
- сотрудник не видит статус и вынужден переспрашивать;
- нет единого журнала решений по заявке.

Employee Service собирает заявку, маршрут согласования и решения в одном месте.

---

## 4. Заинтересованные стороны

| Сторона | Интерес |
| :--- | :--- |
| Сотрудник (инициатор) | Быстро подать заявку, видеть статус, доработать заявку после возврата |
| Согласующий (руководитель, кадровая служба и др.) | Иметь очередь заявок и принимать решения |
| Владелец процесса (вне системы в MVP) | Прозрачность и единообразие процесса |
| Автор проекта | Трассируемый комплект артефактов для портфолио |

Администратор процессов относится к будущему развитию (см. [Backlog](../backlog.md)).

## 5. Роли

| Роль | Код | Описание |
| :--- | :--- | :--- |
| Сотрудник | `employee` | Создаёт заявки из каталога, отслеживает свои заявки, дорабатывает возвращённые |
| Согласующий | `approver` | Обрабатывает заявки, назначенные на его этап |

Отдельные роли «Руководитель» и «HR» не выделяются: это пользователи с ролью `approver`, назначенные на нужные этапы маршрута. Пользователь может иметь обе роли.

В MVP нет настоящего входа в систему: роль выбирается на стартовом экране и передаётся в заголовке запроса. Это техническое упрощение демо, полноценная аутентификация вынесена в backlog.

## 6. Scope MVP

1. **Каталог заявок** — просмотр 2–3 предустановленных типов (например, отпуск, справка) с описанием и полями формы.
2. **Создание и отправка заявки** — заполнение формы, сохранение черновика, отправка на согласование.
3. **Мои заявки и карточка заявки** — список со статусами, детальный просмотр, комментарии, история решений и смены статусов.
4. **Согласование** — последовательный маршрут, очередь согласующего, решения approve / reject / return.
5. **Возврат на доработку** — статус `returned`, редактирование инициатором, повторная отправка с того же этапа.
6. **Отмена заявки** — только в статусах `draft` и `returned`.
7. **Фиксация маршрута** при отправке заявки: изменения настроек не влияют на уже отправленные заявки (подробности в [Snapshot Model](../03-diagrams/erd/snapshot-model.md)).
8. **Технический контур** — REST API, OpenAPI, PostgreSQL, лёгкий веб-клиент из 5 экранов: выбор роли, мои заявки, создание заявки, карточка заявки, очередь согласующего.

Типы заявок, маршруты и назначения согласующих заданы начальными данными (seed) и через интерфейс не настраиваются.

## 7. Вне scope

- автоопределение руководителя по оргструктуре;
- параллельные этапы и условные ветвления маршрута;
- полноценный BPM-движок;
- SSO / AD / LDAP, 2FA;
- email- и push-уведомления, файловые вложения;
- версионирование типов заявок;
- мультитенантность;
- HRIS, payroll, электронная подпись;
- мобильное приложение, визуальный редактор процессов.

## 7.1. Отложено (backlog)

Уже проработано в документации, но не входит в MVP: вход и JWT, личный кабинет и профиль, in-app уведомления, административная панель (типы заявок, маршруты, справочники), административный журнал действий и реестр всех заявок. Подробности в [Backlog](../backlog.md).

## 9. Допущения

1. Система обслуживает одно предприятие.
2. Пользователи, роли, типы заявок, маршруты и назначения созданы начальными данными для демо.
3. Согласующие назначены явно: по роли или по конкретному пользователю.
4. На этапе с несколькими согласующими достаточно одного approve (first-approve wins).
5. Маршрут строго последовательный.
6. Маршрут фиксируется при отправке заявки.
7. Аналитическая документация равноправна коду в поставке проекта.
8. Язык артефактов — русский.

## 10. Ограничения

| Тип | Ограничение |
| :--- | :--- |
| Организационное | Одно предприятие |
| Процессное | Нет параллельных этапов и автомаршрутизации по оргструктуре |
| Безопасность | Нет входа, SSO, 2FA; роль передаётся заголовком (только для демо) |
| Контент | Нет файловых вложений |
| Платформа | Веб (браузер); нативного клиента нет |
| Движок | Встроенный последовательный approval engine, не внешний BPM |
| Конфигурация | Изменение маршрута не действует на уже отправленные заявки |

## 11. Критерии успеха

1. **Документация:** есть Vision, требования, диаграммы процессов и состояний, ERD, OpenAPI-контракт, критерии приёмки; связи между ними прослеживаются по ID.
2. **Демо-сценарий:** сотрудник создаёт и отправляет заявку → согласующий согласует, отклоняет или возвращает → сотрудник видит статус и при возврате дорабатывает и отправляет повторно.
3. **Маршрут:** для типа заявки задан последовательный маршрут; на этапе с несколькими согласующими срабатывает first-approve wins.
4. **Фиксация маршрута:** изменение настроек не влияет на уже отправленные заявки.
5. **Отмена:** возможна только для `draft` и `returned`.
6. **Технологии:** API соответствует OpenAPI; сервис работает локально и в облаке (Render + Neon).
7. **Портфолио:** по документам можно проследить путь от проблемы до реализации без пояснений автора.

---

## 12. Зафиксированные решения

1. First-approve wins на этапе с несколькими согласующими.
2. Возврат на доработку: `returned` → редактирование → повторная отправка с того же этапа.
3. Отмена инициатором только для `draft` и `returned`.
4. Назначения согласующих явные, без автоопределения по оргструктуре.
5. Маршрут последовательный.
6. Маршрут фиксируется при отправке заявки.
7. Роль передаётся заголовком запроса, настоящей аутентификации в MVP нет.
8. Интерфейс: лёгкий веб-клиент (статические HTML-страницы с JavaScript, отдаёт FastAPI), без React/SPA.
9. Административная панель, уведомления, профиль и журнал действий отложены в backlog.
