# Vision & Scope

**Проект:** Employee Service  
**Документ:** Vision and Scope  
**Версия:** 1.0  
**Статус:** Draft (Этап 1)  
**Связанные артефакты:** [Глоссарий](./glossary.md)

---

## 1. Цель системы

Employee Service — веб-система личного кабинета сотрудника и сервиса подачи заявок.

Система позволяет сотруднику:

- войти в личный кабинет и просмотреть свои данные;
- выбрать услугу из каталога типов заявок;
- создать заявку и отслеживать её статус;
- получать in-app уведомления о ходе согласования.

Заявки проходят согласование по маршруту. Маршрут зависит от типа заявки и настроек процесса. Администратор настраивает типы заявок, этапы согласования, последовательность этапов, назначения согласующих, справочники, а также просматривает заявки и историю изменений.

---

## 2. Цель pet-project

Цель проекта — продемонстрировать навыки системного аналитика на сквозном примере: от описания предметной области и требований до архитектуры, модели данных, API-контрактов и работающего MVP.

Проект включает не только реализацию (PostgreSQL, FastAPI, React + TypeScript, Docker Compose, REST, OpenAPI), но и полноценную аналитическую документацию: функциональные и нефункциональные требования, бизнес-правила, пользовательские сценарии, BPMN, UML, архитектуру, ERD, описание БД, API-контракты, матрицу ошибок и acceptance criteria.

---

## 3. Problem statement

В организациях сотрудники часто подают типовые внутренние заявки (кадровые, административные, на доступ к системам) через разрозненные каналы: почту, мессенджеры, бумажные формы. Из-за этого:

- инициатор не видит актуальный статус заявки;
- маршрут согласования зависит от устных договорённостей и легко нарушается;
- нет единого журнала решений и истории изменений;
- администратору сложно менять типы заявок и цепочки согласования без доработки системы.

Employee Service решает эту проблему единым личным кабинетом, каталогом услуг, конфигурируемым последовательным маршрутом согласования и аудитом действий.

---

## 4. Stakeholders

| Stakeholder | Интерес |
| :--- | :--- |
| Сотрудник (инициатор) | Быстро подать заявку, видеть статус, получать уведомления, при необходимости доработать заявку после возврата |
| Согласующий | Иметь очередь задач, принимать решение (approve / reject / return) |
| Администратор процессов | Настраивать типы заявок, маршруты, назначения, справочники без изменения кода |
| Руководство / владелец процесса (внешний к системе в MVP) | Прозрачность прохождения заявок и единообразие процесса |
| Системный аналитик (автор pet-project) | Полный комплект аналитических артефактов и трассируемый MVP для портфолио |

---

## 5. Пользователи и роли

В MVP используются системные роли:

| Роль | Код | Описание |
| :--- | :--- | :--- |
| Сотрудник | `employee` | Владелец личного кабинета; создаёт заявки из каталога; отслеживает свои заявки; редактирует заявки в статусе `returned` |
| Согласующий | `approver` | Обрабатывает задачи согласования, на которые он назначен (лично или через роль) |
| Администратор | `admin` | Управляет типами заявок, маршрутами, этапами, назначениями, справочниками; просматривает заявки и историю |

Один пользователь может иметь несколько ролей (например, `employee` + `approver`).

Отдельные бизнес-роли «Руководитель» и «HR» в MVP не выделяются как системные: соответствующие участники назначаются на этапы маршрута как пользователи с ролью `approver` (по роли или по конкретному пользователю).

---

## 6. Scope (в границах MVP)

В scope MVP входят:

1. **Аутентификация и сессия** — вход по логину/паролю, JWT, текущий пользователь, авторизация по ролям.
2. **Личный кабинет сотрудника** — просмотр профиля (ФИО, email, должность, отдел).
3. **Каталог заявок** — список активных типов заявок с описанием и схемой полей формы.
4. **Создание заявки** — заполнение формы по типу, отправка на согласование.
5. **Список и карточка заявки** — просмотр своих заявок (сотрудник), реестр заявок (администратор), статусы, комментарии.
6. **Согласование** — последовательный маршрут; очередь задач согласующего; решения approve / reject / return; правило first-approve wins на этапе с несколькими согласующими.
7. **Возврат на доработку** — статус `returned`; редактирование инициатором; повторная отправка с того же этапа.
8. **Отмена инициатором** — только для статусов `draft` и `returned`.
9. **Уведомления** — только in-app (новая задача, смена статуса и связанные события).
10. **История действий** — журнал значимых событий по заявке.
11. **Административная панель** — создание и изменение типов заявок; настройка этапов и их последовательности; назначение ролей/пользователей на этапы; управление справочниками; просмотр заявок и истории.
12. **Snapshot маршрута** — при отправке заявки маршрут фиксируется; последующие изменения настроек не влияют на уже запущенные заявки.
13. **Технический контур** — PostgreSQL, REST API, OpenAPI, backend (Python + FastAPI), frontend (React + TypeScript), Docker Compose.
14. **Аналитическая документация** — по утверждённому плану проекта.

Предустановленные примеры типов заявок для демонстрации (ориентир): отпуск, справка 2-НДФЛ, доступ к системе.

---

## 7. Out of scope

Явно исключено из MVP и не входит в текущую версию системы:

- автоматическое определение руководителя через оргструктуру / дерево подразделений;
- параллельные этапы согласования и условные ветвления маршрута;
- полноценный BPM-движок (Camunda и аналоги);
- SSO / интеграция с корпоративным каталогом (AD/LDAP);
- 2FA;
- email- и push-уведомления;
- файловые вложения;
- версионирование типов заявок (кроме `is_active` и snapshot маршрута при submit);
- мультитенантность (несколько предприятий);
- полноценный HRIS / payroll / кадровый учёт;
- электронная подпись;
- мобильное приложение;
- drag-and-drop визуальный редактор процессов.

## 9. High-level assumptions

1. Система обслуживает **одно предприятие**.
2. Пользователи и роли создаются/наполняются для демо (seed); полноценный IAM не требуется.
3. Согласующие назначаются **явно**: по роли и/или по конкретному пользователю.
4. На этапе с несколькими согласующими достаточно **одного approve** (first-approve wins) для перехода на следующий этап.
5. Маршрут согласования в MVP **строго последовательный**.
6. При отправке заявки сохраняется **snapshot маршрута**.
7. Уведомления доставляются только **внутри приложения**.
8. Данные профиля сотрудника хранятся в системе как атрибуты пользователя (без синхронизации с внешней HR-системой в MVP).
9. Аналитическая документация является равноправной частью поставки pet-project наряду с кодом.
10. Язык артефактов документации — русский.

## 10. Ограничения

| Тип | Ограничение |
| :--- | :--- |
| Организационное | Один тенант (одно предприятие) |
| Процессное | Нет параллельных этапов; нет auto-routing по оргструктуре |
| Каналы связи | Нет email/push |
| Безопасность | Нет SSO и 2FA в MVP; базовая аутентификация JWT |
| Контент заявки | Нет файловых вложений в MVP |
| Платформа | Web (desktop/mobile browser); отдельного native-клиента нет |
| Движок процессов | Встроенный последовательный approval engine, не внешний BPM |
| Изменение конфигурации | Изменения маршрута не ретроактивны для уже запущенных заявок |

## 11. Критерии успеха MVP

MVP считается успешным, если выполнены все пункты:

1. **Документация Этапа 1+:** есть Vision & Scope и глоссарий; далее по плану — требования, диаграммы, OpenAPI, acceptance criteria.
2. **Сквозной демо-сценарий:** сотрудник создаёт заявку из каталога → согласующий approve/reject/return → инициатор видит статус и историю → при return может доработать и повторно отправить.
3. **Маршрут:** для типа заявки настроен последовательный маршрут с назначениями; на этапе с несколькими согласующими срабатывает first-approve wins.
4. **Snapshot:** изменение маршрута администратором не меняет поведение уже отправленных заявок.
5. **Отмена:** инициатор может отменить только `draft` и `returned`.
6. **Админка:** администратор может создать/изменить тип заявки, этапы, последовательность, назначения и справочник; просмотреть заявки и историю.
7. **Уведомления:** ключевые события отражаются in-app.
8. **Технологии:** система поднимается через Docker Compose; API соответствует OpenAPI; используются PostgreSQL, FastAPI, React + TypeScript.
9. **Портфолио:** по артефактам можно проследить путь от бизнес-потребности до реализации без привлечения авторов проекта.

## 12. Зафиксированные продуктовые решения (baseline)

Следующие решения утверждены и являются baseline для последующих этапов:

1. First-approve wins на этапе с несколькими согласующими.
2. Поддерживается возврат на доработку: `returned` → редактирование → повторная отправка с того же этапа.
3. Отмена инициатором только для `draft` и `returned`.
4. Нет автоопределения руководителя через оргструктуру; назначения явные.
5. Нет параллельных этапов; маршрут последовательный.
6. Snapshot маршрута при отправке заявки.
7. Уведомления только in-app.
8. Одно предприятие.
9. Нет SSO, 2FA, email/push, файловых вложений и полноценного BPM-движка.
