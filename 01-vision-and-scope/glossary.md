## A–Z / системные имена

### Employee Service
Веб-система личного кабинета сотрудника и сервиса подачи и согласования заявок. Название продукта pet-project.

### Approval Engine
Встроенный механизм последовательного согласования заявок по snapshot маршрута. Не является внешним BPM-движком.

### First-approve wins
Правило этапа: если на этап назначено несколько согласующих, достаточно одного решения `approve` для перехода заявки на следующий этап (или в статус `approved`, если этап последний).

### Snapshot маршрута
Копия маршрута согласования (этапы, порядок, назначения), зафиксированная в момент отправки заявки. Последующие изменения настроек типа заявки / маршрута не влияют на уже запущенные заявки.

### JWT
JSON Web Token — способ аутентификации сессии пользователя в MVP (без SSO).

## Роли и участники

### Инициатор
Пользователь, создавший заявку. В типичном сценарии — сотрудник. Инициатор отслеживает статус, может отменить заявку в статусах `draft` и `returned`, а также доработать заявку после возврата.

### Сотрудник (`employee`)
Системная роль пользователя личного кабинета. Может просматривать профиль, создавать заявки из каталога, работать со своими заявками и получать in-app уведомления.

### Согласующий (`approver`)
Системная роль пользователя, участвующего в согласовании. Обрабатывает задачи согласования, на которые назначен лично или через роль. Бизнес-роли вроде «руководитель» или «HR» в MVP моделируются через назначения на этапы, а не отдельными системными ролями.

### Администратор (`admin`)
Системная роль для настройки типов заявок, маршрутов, этапов, назначений, справочников, а также для просмотра заявок и истории изменений.

### Assignee (назначенный)
Пользователь или носитель роли, указанный в назначении этапа и получающий задачу согласования.

## Каталог и заявки

### Каталог заявок (каталог услуг)
Список активных типов заявок, доступных сотруднику для создания заявки.

### Тип заявки
Конфигурируемая услуга каталога: название, описание, признак активности, схема полей формы и связанный маршрут согласования.

### Поле типа заявки
Элемент схемы формы типа заявки (например, текст, дата, число, значение из справочника). Определяет, какие данные сотрудник заполняет при создании заявки.

### Заявка
Экземпляр типа заявки, созданный инициатором. Содержит значения полей, текущий статус, привязку к snapshot маршрута, историю и связанные задачи согласования.

### Черновик
Заявка в статусе `draft`, ещё не отправленная на согласование (если создание черновика поддерживается процессом создания).

### Статус заявки
Текущее состояние жизненного цикла заявки в MVP:

| Код | Смысл |
| :--- | :--- |
| `draft` | Черновик; не на согласовании |
| `in_approval` | На согласовании |
| `returned` | Возвращена на доработку инициатору |
| `approved` | Согласована по всем этапам маршрута |
| `rejected` | Отклонена на одном из этапов |
| `cancelled` | Отменена инициатором |

### Значение поля заявки
Конкретные данные, введённые инициатором по схеме полей типа заявки.

### Комментарий
Текстовое пояснение к заявке или к решению по этапу (например, причина возврата или отклонения).

## Согласование

### Маршрут согласования (маршрут)
Упорядоченная последовательность этапов, по которой проходит заявка данного типа. В MVP маршрут всегда последовательный (без параллельных этапов).

### Этап согласования (этап)
Один шаг маршрута с порядковым номером (sequence) и набором назначений согласующих.

### Назначение на этап
Правило, кто может согласовать этап: роль и/или конкретный пользователь. Назначения задаются администратором явно; автоматический выбор руководителя из оргструктуры в MVP отсутствует.

### Задача согласования
Рабочий элемент для согласующего по конкретному этапу конкретной заявки. Создаётся системой при входе заявки на этап.

### Очередь задач
Список открытых задач согласования текущего пользователя-согласующего.

### Согласование (approve)
Положительное решение по задаче этапа. При first-approve wins переводит заявку на следующий этап или в статус `approved`.

### Отклонение (reject)
Отрицательное решение по задаче этапа. Завершает заявку со статусом `rejected`.

### Возврат на доработку (return)
Решение согласующего вернуть заявку инициатору. Заявка получает статус `returned`. После редактирования инициатор повторно отправляет заявку на согласование **с того же этапа**.

### Отмена заявки
Действие инициатора, переводящее заявку в статус `cancelled`. В MVP разрешено только для статусов `draft` и `returned`.

## Уведомления, история, администрирование

### Уведомление (in-app)
Сообщение внутри системы пользователю о событии (например, новая задача согласования или смена статуса заявки). Каналы email и push в MVP отсутствуют.

### История действий (история изменений)
Журнал значимых событий по заявке (и при необходимости по конфигурации): кто, когда, какое действие, предыдущее и новое состояние, комментарий.

### Справочник
Управляемый администратором набор справочных значений, используемых в полях форм и классификации.

### Элемент справочника
Отдельное значение справочника (код/наименование, признак активности).

### Административная панель (админка)
Часть системы для администратора: настройка типов заявок, этапов, последовательности, назначений, справочников; просмотр заявок и истории.

### Личный кабинет
Часть системы для сотрудника: профиль, каталог, свои заявки, уведомления.

## Технические термины MVP

### REST API
HTTP-интерфейс backend-части системы; контракт описывается в OpenAPI.

### OpenAPI
Спецификация контракта REST API (источник истины для эндпоинтов, схем и ошибок).

### PostgreSQL
Реляционная СУБД, используемая для хранения данных системы.

### MVP
Minimal Viable Product — минимально достаточная версия системы в утверждённых границах scope, демонстрирующая сквозной сценарий подачи и согласования заявок.
