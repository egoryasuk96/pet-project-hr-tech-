## 1. Назначение

NFR задают проверяемые ограничения качества MVP. Значения, которые нельзя строго обосновать из бизнес-требований, помечены **TBD** с предложенным вариантом.

## 2. Performance

### NFR-PERF-01 — Время ответа API (чтение)
Для 95% успешных read-запросов (профиль, каталог, список своих заявок, очередь задач, карточка заявки) время ответа backend при нагрузке до 20 одновременных пользователей ≤ **500 мс** (исключая холодный старт контейнера).  
**Проверка:** нагрузочный/смоук-сценарий с замером latency p95.

### NFR-PERF-02 — Время ответа API (запись)
Для 95% успешных write-операций (создание заявки, submit, approve/reject/return, CRUD админки) время ответа ≤ **1000 мс** при той же нагрузке.  
**Проверка:** замеры p95 на критичных сценариях.

### NFR-PERF-03 — Пагинация списков
Списки заявок, задач, уведомлений и реестра админа поддерживают пагинацию. Размер страницы по умолчанию **20**, максимум **100**.  
**Проверка:** запрос с `page_size=101` отклоняется валидацией.

### NFR-PERF-04 — Объём демо-данных
**TBD.** Предложение: система корректно работает при ≥ 1 000 заявок и ≥ 5 000 записей истории без деградации p95 за пределы NFR-PERF-01/02 на локальном Docker Compose.

## 3. Availability

### NFR-AVL-01 — Режим поставки MVP
Целевой режим — локальный/демо-стенд через Docker Compose. SLA production **не применяется**.  
**Проверка:** `docker compose up` поднимает db + api + web без ручных шагов кроме documented env.

### NFR-AVL-02 — Восстановление после рестарта
После рестарта контейнеров api/db данные PostgreSQL сохраняются в volume; сессии JWT не требуют sticky-state на сервере.  
**Проверка:** restart api/db → данные заявок на месте; валидный токен продолжает работать до expiry.

## 4. Security

### NFR-SEC-01 — Аутентификация
Доступ к защищённым операциям возможен только с валидным JWT. Невалидный/просроченный токен → HTTP 401.  
**Проверка:** запросы без токена и с битым токеном.

### NFR-SEC-02 — Авторизация по ролям и владению
Доступ разграничивается по ролям и правилам BR-01, BR-13–15, BR-21. Нарушение → HTTP 403.  
**Проверка:** AC-ACC-01, AC-ACC-02 и матрица RBAC.

### NFR-SEC-03 — Хранение паролей
Пароли хранятся только в виде хеша (алгоритм: **bcrypt** или **argon2**; выбрать один на этапе реализации). Plain-text запрещён.  
**Проверка:** инспекция БД / unit-тест хеширования.

### NFR-SEC-04 — Срок жизни токена
**TBD.** Предложение: access token TTL = **8 часов**; refresh tokens в MVP отсутствуют (повторный login).  
**Проверка:** токен старше TTL → 401.

### NFR-SEC-05 — Защита от перечисления чужих ресурсов
Запрос чужой заявки сотрудником возвращает **404** или **403** единообразно (выбрать одно на этапе API; предложение: **404** для скрытия факта существования).  
**Проверка:** AC-ACC-01.

### NFR-SEC-06 — HTTPS
**TBD для production.** В локальном Docker Compose допустим HTTP. Для любого внешнего демо-стенда — HTTPS обязателен.

## 5. Reliability

### NFR-REL-01 — Целостность перехода статусов
Переходы статусов заявки и задач выполняются атомарно с записью истории: не допускается «approve без истории» или «смена статуса без закрытия задач этапа» при first-approve.  
**Проверка:** интеграционные тесты BR-03, BR-04, BR-05, BR-20.

### NFR-REL-02 — Идемпотентность повторного действия
Повторный approve/reject/return по уже завершённой задаче не меняет состояние повторно и возвращает ошибку duplicate/invalid state.  
**Проверка:** error-matrix ERR-DUP-ACTION, ERR-TASK-DONE.

### NFR-REL-03 — Сохранность snapshot
Snapshot маршрута после первого submit неизменяем прикладными операциями.  
**Проверка:** AC-APP-10.

## 6. Maintainability

### NFR-MNT-01 — OpenAPI как контракт
Публичный REST API описывается OpenAPI 3.x и соответствует реализации (Этап 4+).  
**Проверка:** сверка спецификации и фактических ответов.

### NFR-MNT-02 — Миграции БД
Схема БД управляется миграциями (Alembic или аналог). Запрещены «ручные» необратимые правки схемы на демо без миграции.  
**Проверка:** чистый подъём БД только миграциями.

### NFR-MNT-03 — Трассируемые ID требований
Код и тесты критичных правил ссылаются на ID FR/BR/AC в комментариях или именах тестов для ключевых сценариев согласования.  
**Проверка:** наличие ссылок в тестах approve/reject/return/snapshot.

## 7. Scalability

### NFR-SCL-01 — Горизонтальное масштабирование API
**TBD.** Предложение для MVP: stateless API (JWT) допускает ≥ 2 инстанса api за балансировщиком без sticky sessions. Фактический multi-instance деплой в MVP не обязателен.  
**Проверка:** архитектурный review + отсутствие server-side session store.

### NFR-SCL-02 — Рост числа типов заявок
Система поддерживает ≥ **50** активных типов заявок и ≥ **10** этапов на маршрут без изменения архитектуры.  
**Проверка:** seed/admin CRUD на граничных значениях.

## 8. Logging / Audit

### NFR-LOG-01 — Технические логи API
API логирует: method, path, status code, latency, request_id, user_id (если аутентифицирован). Пароли и токены в лог не пишутся.  
**Проверка:** sample логов на login и submit.

### NFR-LOG-02 — Прикладной аудит заявок
Значимые бизнес-события пишутся в историю заявки (BR-24) с actor, timestamp, action, from/to, comment.  
**Проверка:** UC-14, FR-AUDIT-01.

### NFR-LOG-03 — Retention
**TBD.** Предложение: история заявок хранится бессрочно в рамках MVP; ротация технических логов — 14 дней или размер volume.

## 9. Usability

### NFR-USB-01 — Понятность статусов
В карточке заявки пользователь видит человекочитаемый статус и текущий этап (если `in_approval`).  
**Проверка:** UI/демо UC-06.

### NFR-USB-02 — Сообщения об ошибках
Пользовательские сообщения соответствуют error-matrix (поле User message) и не раскрывают stack trace.  
**Проверка:** негативные сценарии login, forbidden, invalid state.

### NFR-USB-03 — Язык интерфейса MVP
UI и пользовательские сообщения — **русский**.  
**Проверка:** смоук UI.

## 10. Deployment

### NFR-DEP-01 — Docker Compose
Проект поставляется с Docker Compose, включающим PostgreSQL, backend, frontend.  
**Проверка:** чистый clone → documented start → login демо-пользователем.

### NFR-DEP-02 — Seed-данные
После первого запуска доступны демо-пользователи всех ролей и ≥ 2 активных типа заявок с валидным маршрутом.  
**Проверка:** login под employee/approver/admin; каталог не пуст.

### NFR-DEP-03 — Конфигурация через env
Секреты (DB URL, JWT secret) задаются переменными окружения, не хардкодятся в репозитории.  
**Проверка:** review конфигурации.
