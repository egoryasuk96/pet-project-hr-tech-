# Функциональные требования

**Проект:** Employee Service

Формат ID: `FR-<AREA>-NN`. Области: AUTH, CAB, CAT, REQ, APP, NOTIF, AUDIT, ADMIN.

## 1. AUTH — Аутентификация и авторизация

### FR-AUTH-01 — Вход в систему
| Поле | Содержание |
| :--- | :--- |
| **Название** | Вход по логину и паролю |
| **Описание** | Пользователь аутентифицируется логином и паролем и получает JWT для последующих запросов |
| **Actor** | Любой зарегистрированный пользователь |
| **Preconditions** | Учётная запись существует и активна |
| **Основной сценарий** | 1) Пользователь вводит логин и пароль 2) Система проверяет учётные данные 3) Система выдаёт JWT и базовые данные пользователя (id, ФИО, роли) |
| **Альтернативы / исключения** | Неверные данные → ERR_INVALID_CREDENTIALS; неактивный пользователь → ERR_FORBIDDEN |
| **Postconditions** | Клиент хранит токен; пользователь считается аутентифицированным до expiry |
| **Связи** | UC-01; NFR-SEC-01; ERR_INVALID_CREDENTIALS |

### FR-AUTH-02 — Текущий пользователь
| Поле | Содержание |
| :--- | :--- |
| **Название** | Получение текущего пользователя |
| **Описание** | Аутентифицированный пользователь получает свой профиль сессии: id, ФИО, email, должность, отдел, роли |
| **Actor** | Аутентифицированный пользователь |
| **Preconditions** | Валидный JWT |
| **Основной сценарий** | 1) Клиент запрашивает текущего пользователя 2) Система возвращает данные по subject токена |
| **Альтернативы / исключения** | Нет/невалидный токен → ERR_UNAUTHORIZED |
| **Postconditions** | Данные не изменяются |
| **Связи** | UC-01, UC-02; FR-CAB-01 |

### FR-AUTH-03 — Авторизация по ролям и правилам
| Поле | Содержание |
| :--- | :--- |
| **Название** | Проверка прав на операцию |
| **Описание** | Перед выполнением операции система проверяет роли (union) и ограничения владения/assignee (RBAC, BR-01, BR-13–16, BR-21) |
| **Actor** | Система |
| **Preconditions** | Аутентифицированный запрос |
| **Основной сценарий** | 1) Определяются роли пользователя 2) Проверяется разрешение функции 3) При необходимости проверяется владение ресурсом / assignee 4) Операция выполняется |
| **Альтернативы / исключения** | Нет прав → ERR_FORBIDDEN / ERR_FORBIDDEN_APPROVAL / ERR_NOT_FOUND |
| **Postconditions** | При отказе состояние не меняется |
| **Связи** | RBAC; AC-ACC-*; все защищённые FR |

## 4. REQ — Жизненный цикл заявки

### FR-REQ-01 — Создание заявки
| Поле | Содержание |
| :--- | :--- |
| **Название** | Создание заявки в статусе draft |
| **Описание** | Сотрудник создаёт заявку выбранного активного типа; статус = `draft` |
| **Actor** | employee |
| **Preconditions** | Тип активен (BR-10) |
| **Основной сценарий** | 1) Выбор типа 2) Создание заявки 3) Система сохраняет draft, инициатор = текущий пользователь |
| **Альтернативы / исключения** | Неактивный тип → ERR_INACTIVE_TYPE |
| **Postconditions** | Заявка `draft`; запись в истории (BR-24) |
| **Связи** | BR-19; UC-04; AC-APP-01 |

### FR-REQ-02 — Заполнение полей
| Поле | Содержание |
| :--- | :--- |
| **Название** | Заполнение / изменение полей заявки |
| **Описание** | Инициатор сохраняет значения полей по схеме типа |
| **Actor** | employee (инициатор) |
| **Preconditions** | Заявка в `draft` или `returned`; пользователь — инициатор |
| **Основной сценарий** | 1) Ввод значений 2) Валидация по схеме 3) Сохранение |
| **Альтернативы / исключения** | Ошибка валидации → ERR_VALIDATION; неверный статус → ERR_INVALID_STATE; не владелец → ERR_NOT_FOUND |
| **Postconditions** | Значения обновлены; при returned — факт изменения отражается в истории (BR-24) |
| **Связи** | BR-06, BR-19; UC-04, UC-09 |

### FR-REQ-03 — Отправка на согласование (submit)
| Поле | Содержание |
| :--- | :--- |
| **Название** | Submit заявки |
| **Описание** | Инициатор отправляет заявку из `draft` (первый submit) или `returned` (повторный). При первом submit создаётся snapshot (BR-08). Статус → `in_approval`. Создаются задачи текущего этапа |
| **Actor** | employee (инициатор) |
| **Preconditions** | Статус `draft` или `returned`; обязательные поля валидны; маршрут валиден (BR-18) |
| **Основной сценарий** | 1) Submit 2) Валидация 3) Snapshot (если первый) 4) Статус in_approval 5) Задачи этапа 6) Уведомления согласующим 7) История |
| **Альтернативы / исключения** | ERR_VALIDATION; ERR_ROUTE_CONFIG; ERR_INVALID_STATE; ERR_INACTIVE_TYPE (если тип деактивирован до первого submit) |
| **Postconditions** | BR-20; задачи созданы; snapshot зафиксирован или переиспользован (BR-22) |
| **Связи** | BR-08, BR-18, BR-20, BR-22; UC-05; AC-APP-02, AC-APP-03, AC-APP-08, AC-APP-10 |

### FR-REQ-04 — Просмотр заявки
| Поле | Содержание |
| :--- | :--- |
| **Название** | Просмотр карточки заявки |
| **Описание** | Авторизованный субъект читает карточку в пределах прав видимости |

| **Альтернативы / исключения** | Нет доступа → ERR_NOT_FOUND / ERR_FORBIDDEN |
| **Postconditions** | — |
| **Связи** | BR-01, BR-13, BR-14; UC-06 |

### FR-REQ-05 — Просмотр статуса

| **Actor** | См. FR-REQ-04 |
| **Preconditions** | Доступ к заявке |
| **Основной сценарий** | Система отдаёт status и current_step (если применимо) |

### FR-REQ-06 — Комментарии
| Поле | Содержание |

| **Связи** | BR-05; UC-09; AC-APP-07 |

| :--- | :--- |

| **Preconditions** | Статус `returned`; BR-06, BR-22 |

| **Postconditions** | `in_approval`; задачи того же этапа созданы заново |
| **Связи** | BR-06, BR-22; UC-05; AC-APP-08 |

## 6. NOTIF — Уведомления

### FR-NOTIF-01 — Создание in-app уведомления
| Поле | Содержание |
| :--- | :--- |
| **Название** | Создание уведомления |
| **Описание** | Система создаёт in-app уведомление получателю при событиях BR-23 |
| **Actor** | Система |
| **Preconditions** | Произошло бизнес-событие |
| **Основной сценарий** | 1) Определение получателей 2) Создание записи (unread) 3) Связь с заявкой/задачей |
| **Альтернативы / исключения** | Сбой создания уведомления не откатывает основную транзакцию бизнес-действия **TBD** (предложение: в одной транзакции) |
