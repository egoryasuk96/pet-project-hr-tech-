## 1. Назначение

Документ фиксирует бизнес-правила MVP, обязательные для реализации и проверки. Правила имеют устойчивые ID `BR-XX` и используются в FR, UC и AC.

---

## 2. Правила доступа и видимости

### BR-01 — Видимость заявок сотрудника
Сотрудник (`employee`) видит только заявки, где он является инициатором.  
**Исключение:** пользователь с ролью `admin` видит все заявки в реестре (см. BR-13).  
**Связи:** FR-REQ-04, FR-ADMIN-07, UC-06, UC-15, AC-ACC-01

### BR-13 — Видимость заявок администратора
Администратор (`admin`) может просматривать реестр всех заявок и историю по любой заявке.  
**Связи:** FR-ADMIN-07, FR-ADMIN-08, UC-15, UC-14

### BR-14 — Видимость заявок согласующего
Согласующий (`approver`) может просматривать заявку, по которой у него есть задача согласования (открытая или завершённая в рамках его участия), а также свою очередь задач. Чужие заявки без связанной задачи недоступны.  
**Связи:** FR-APP-01, FR-APP-02, UC-07

### BR-15 — Действие только по своей задаче
Согласующий может выполнить approve / reject / return только по задаче, где он является assignee (лично или через роль, по которой задача создана для него), и только если задача в статусе открыта.  
**Связи:** FR-APP-03, FR-APP-04, FR-APP-05, AC-ACC-02

### BR-16 — Множественные роли
Один пользователь может иметь несколько системных ролей одновременно (`employee`, `approver`, `admin`). Права объединяются (union).  
**Связи:** FR-AUTH-03, матрица RBAC

## 3. Правила маршрута и согласования

### BR-02 — Последовательный маршрут
Маршрут согласования выполняется строго последовательно: следующий этап начинается только после успешного завершения предыдущего. Параллельные этапы в MVP не используются.  
**Связи:** FR-APP-06, UC-07, AC-APP-05

### BR-03 — First-approve wins
Если на этап назначено несколько согласующих, достаточно одного успешного `approve` для завершения этапа и перехода дальше (или завершения маршрута). Остальные открытые задачи того же этапа закрываются системой как утратившие актуальность.  
**Связи:** FR-APP-03, FR-APP-06, AC-APP-09

### BR-04 — Reject завершает заявку
Решение `reject` на любом этапе переводит заявку в статус `rejected` и завершает маршрут. Последующие этапы не создаются.  
**Связи:** FR-APP-04, UC-08, AC-APP-06

### BR-05 — Return на доработку
Решение `return` переводит заявку в статус `returned`, закрывает открытые задачи текущего этапа и возвращает заявку инициатору на доработку. Текущий номер этапа сохраняется для последующего повторного submit.  
**Связи:** FR-REQ-08, FR-APP-05, UC-09, AC-APP-07

### BR-17 — Завершение маршрута
Если выполнен `approve` на последнем этапе snapshot маршрута, заявка переходит в статус `approved`.  
**Связи:** FR-APP-07, AC-APP-05

### BR-18 — Маршрут обязан быть валиден при submit
При отправке заявки тип должен быть активен, маршрут должен содержать минимум один этап, каждый этап должен иметь хотя бы одно назначение (роль и/или пользователь). Иначе submit отклоняется с ошибкой конфигурации.  
**Связи:** FR-REQ-03, FR-ADMIN-03, ERR-ROUTE-CONFIG

### BR-12 — Нет auto-routing по оргструктуре
Система не определяет согласующего автоматически через оргструктуру или «непосредственного руководителя». Назначения задаются явно: роль и/или конкретный пользователь.  
**Связи:** FR-ADMIN-05, Vision §12

## 4. Правила жизненного цикла заявки

### BR-06 — Повторная отправка после return
После `return` инициатор может изменить значения полей заявки (в статусе `returned`) и повторно отправить её на согласование. Повторный submit возобновляет согласование **с того же этапа**, на котором был выполнен return (по snapshot).  
**Связи:** FR-REQ-09, UC-05, AC-APP-08

### BR-07 — Отмена только draft и returned
Инициатор может отменить заявку только в статусах `draft` и `returned`. Отмена переводит заявку в `cancelled`. Отмена из `in_approval`, `approved`, `rejected`, `cancelled` запрещена.  
**Связи:** FR-REQ-07, UC-10, AC-REQ-07

### BR-19 — Создание заявки как draft
Создание заявки (без submit) сохраняет её в статусе `draft`. Редактирование полей до первой отправки допускается только инициатором и только в `draft` (и в `returned` после возврата — см. BR-06).  
**Связи:** FR-REQ-01, FR-REQ-02, UC-04

### BR-20 — Submit переводит в in_approval
Успешный submit из `draft` или повторный submit из `returned` переводит заявку в `in_approval`, создаёт задачи текущего этапа и фиксирует/использует snapshot согласно BR-08 / BR-06.  
**Связи:** FR-REQ-03, UC-05, AC-APP-02, AC-APP-03

### BR-21 — Запрет самосогласования в MVP
Инициатор заявки не может выполнять approve / reject / return по своей заявке, даже если он назначен на этап как согласующий.  
**Связи:** FR-APP-03–05  
**Обоснование:** снижает риск обхода контроля в демо; см. Open Questions, если нужно ослабить.

## 5. Правила snapshot и каталога

### BR-08 — Snapshot при submit
При первой отправке заявки из `draft` система создаёт snapshot маршрута (этапы, порядок, назначения) и сохраняет его с заявкой.  
**Связи:** FR-REQ-03, AC-APP-10

### BR-09 — Изоляция запущенных заявок от изменений конфигурации
Изменение настроек типа заявки, маршрута, этапов или назначений администратором не изменяет snapshot уже отправленных заявок и не меняет их дальнейшее согласование.  
**Связи:** FR-ADMIN-03–05, AC-APP-10

### BR-22 — Повторный submit не пересоздаёт snapshot
При повторной отправке из `returned` используется ранее сохранённый snapshot; новый snapshot не создаётся.  
**Связи:** FR-REQ-09, AC-APP-08, AC-APP-10

### BR-10 — Неактивный тип скрыт в каталоге
Тип заявки с `is_active = false` не отображается в каталоге сотрудника и недоступен для создания новой заявки. Уже созданные заявки этого типа продолжают обрабатываться.  
**Связи:** FR-CAT-01, FR-REQ-01, AC-CAT-01

## 6. Правила уведомлений и аудита

### BR-11 — Уведомления только in-app
В MVP уведомления доставляются только внутри приложения. Email и push не используются.  
**Связи:** FR-NOTIF-01–03, UC-13

### BR-23 — Обязательные события уведомлений
Система создаёт in-app уведомление как минимум при: назначении новой задачи согласующему; смене статуса заявки для инициатора (в т.ч. approve этапа / reject / return / approved / cancelled — по факту события).  
**Связи:** FR-NOTIF-01

### BR-24 — История обязательна для значимых событий
По заявке фиксируется история как минимум для: создания; submit; решений approve/reject/return; перехода этапа; завершения маршрута; отмены; изменений полей при доработке (returned).  
**Связи:** FR-AUDIT-01, FR-AUDIT-02, UC-14
